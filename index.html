01

Product 01

XpressPOS

Restaurant point of sale  ·  Android

Production APK delivered

The problem

A busy front-of-house has to seat guests by dining section, fire orders to the kitchen, then settle a bill in whichever of five payment modes the guest chooses — and it has to survive a full dinner service without losing a table's state.

What I built

  • API-backed login and session handling.
  • Home screen with a dining-section selector and a CardView table grid.
  • Menu and Cart screens on a one-time REST menu fetch into SQLite, with a manual Sync Data control — so service continues when the network doesn't.
  • Table Summary and bill settlement across Cash, Card, UPI, Cheque and NEFT: settle, credit, modify, cancel, bill-to-room and reprint.
  • Item-level order actions, plus waiter/captain assignment and PAX capture.

The part I'd point at in an interview

A reusable, API-driven User Authority permission module. Role checks resolve from the backend instead of being hard-coded per screen, so a venue can change what a waiter may cancel or reprint without me shipping a new build.

03 — Engineering depth

The unglamorous parts are the parts that matter.

Anyone can show a screen they built. These are the decisions underneath — the ones that decide whether an app survives contact with a real restaurant at 9pm on a Saturday.

Live-database surgery

Executed ALTER TABLE schema migrations against live production data in SQL Server (SSMS), and diagnosed then recovered lost schemas and data on the live Xpress KOT database — restoring restaurant operations. Working on a database you cannot afford to drop teaches you to read before you write.

Offline-first by design

The POS menu is fetched once over REST into SQLite, with an explicit manual Sync Data control. Venue Wi-Fi is not a guarantee, and an order screen that needs it is an order screen that fails during service.

Atomicity where it hurts

Transfer and Merge Table operations are handled atomically. A half-applied merge is worse than a visible error, because the kitchen keeps working from data that is quietly wrong.

Background work on modern Android

Call-log sync uses WorkManager and BroadcastReceiver within Android 12–15 background-execution limits. The constraint is designed around, not fought — a foreground service burning battery to dodge the restriction would fail review anyway.

Reusable before clever

Two modules earned their keep: the API-driven User Authority permission layer and a parameterized custom alert-dialog module. Both replaced copy-paste across many screens, and both made the next feature cheaper to build.

Legibility is a feature

Dynamic font sizing on Xpress KOT and admin-adjustable scaling on the TV display. The person reading a ticket is standing three metres away, mid-service, in a hot kitchen.

Actually shipping

Release builds taken through to a delivered production APK and a signed AAB, with multi-resolution testing before deployment. Code that never leaves a debug build is a hobby.

Daily stack

Java, Android SDK, REST APIs, SQLite, SQL Server, Git and Logcat — plus Firebase Authentication and Realtime Database offline persistence from the training phase.
